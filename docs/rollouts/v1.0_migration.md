# V1.0 Migration & Rollout Plan

## 1. Canary Criteria
The updated Cryptonite stack (v1.0) introduces major structural changes to authentication, the kill-switch, and storage atomicity. A canary deployment should run in the `staging` environment first.
**Success Metrics for Canary:**
- 100% of internal Agent Worker traffic authenticated via HMAC without `401/403` spikes.
- Zero "Path Traversal" attempts successfully returning file contents.
- `TRIP_KILL_SWITCH` commands successfully latch the generation and enqueue within the same transaction.
- Pending-Batch ingestion correctly drops incomplete parquet artifacts on restart.

## 2. Rollback Criteria
If any of the following occur during the production rollout, an immediate rollback to `v0.9` is required:
- **Order Admission Failure**: The kill-switch fencing cache fails closed, preventing valid orders from being admitted.
- **Operator Lockout**: The new unified policy dependency (`require_operator`) incorrectly rejects valid TOTP-authenticated sessions.
- **Analytics Drift**: The session-level advisory lock prevents multiple ingestion workers from processing, causing a backlog of >10,000 pending bars.

**Rollback Execution:**
1. Revert the docker-compose image tags.
2. Downgrade Alembic: `alembic downgrade 010` (Note: this drops `machine_tokens` and custom RBAC roles).
3. Restore `apps/web/next.config.mjs` routing to port 8085.

## 3. Legacy-Format Removal
Once `v1.0` is proven stable for 7 days:
- Remove legacy AES fallback keys (`000000000...`) completely from the environment.
- Drop any remaining unauthenticated legacy endpoints (if they were only deprecated and not removed).
- Remove `init-roles.sql` backups.
