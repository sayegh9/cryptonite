# ADR 0004: Mandates, the autonomy ladder, approvals and the notifier (Phase 5)

- Status: Accepted (2026-09-30), pending operator sign-off at Gate 5
- Context: [AI-first blueprint](../ai-first-blueprint.md) §4.4–§4.6, §7.1, §10, decisions D8–D11 and O1/O2, Phase 5 (A5.1–A5.7)
- Branch: `feat/ai-first-phase5` (cut from `feat/ai-first-phase0` at `bb35543`), PR to `feat/ai-first-phase0`

## Decisions

1. **One contract, importable everywhere.** `cryptonite_schemas.mandate` holds the mandate model, levels, statuses, reject codes and the D8 timeout policy as pure code. The orchestrator, API, debate worker and notifier all read the same rules; the ceilings are repeated as DB `CHECK`s in migration `025` (position ≤ 25% of budget, hard stop ≤ 20%, leverage ≤ 5, perps only at L3).
2. **The mandate check runs in the AI order path, before `GuardedOrderDispatcher`, and can only reject** (`cryptonite_execution.mandates.check_mandate`, `cryptonite_orchestrator.mandate_gate`). An order is AI-originated when it is a `SUBMIT_ORDER`, targets an AI instance (`AI_DEBATE_WORKER` or `AI_MANDATE_*`), or comes from an `ai:` requester. Such an order without a mandate is rejected (`MANDATE_REQUIRED`). The dispatcher is not modified; an accepted order is still evaluated by it in full (property-tested: the check never mutates the intent and the dispatcher's verdict is identical with or without it).
3. **Each mandate trades under its own paper instance, `AI_MANDATE_<uuid-hex>`.** This is what attributes positions, fills and PnL to a mandate. The instance row is created on first use (status `SYSTEM`, so the strategy loader never runs it). A mandate may not enter an instrument that someone else holds or works (`MANDATE_INSTRUMENT_CONFLICT`) and may only sell what it holds (`MANDATE_POSITION_NOT_OWNED`), because the dispatcher's spot ledger is account-level.
4. **Mandate orders are sized as a share of the mandate budget** ("6% of mandate ($600)", as in the §7.2 template), not of account cash. Allocations from a debate are capped at the mandate's own position limit before anything is queued, so a model never "breaches" by over-sizing.
5. **Equity, high-water mark and the O2 stops live in the orchestrator's risk monitor** (every 5 s). Mandate equity = budget + spot fill cash flow (fees included) + open positions at the live bid + perp PnL. Drawdown ≥ `max_drawdown_pct`: HALTED, demoted to L1, pending ADD_RISK approvals cancelled, each position closed with a PAPER `CLOSE_POSITION` capped at the mandate's quantity, Critical alert. It stays latched until the operator resumes it with TOTP, which re-bases the high-water mark. Drawdown ≥ half the stop demotes one level, once per episode. The account-wide 20% backstop trips and persists the PAPER kill switch (the latch), halts every mandate at L1 and closes every AI-owned position; its high-water mark re-bases at the next kill-switch reset.
6. **Approvals (`ai_approvals`, migration `026`) are the single place an AI action waits for the operator.** Policy per D8: ADD_RISK times out as *no* (L1, and L2 outside active hours); an L2 veto window inside the operator's active hours proceeds; REDUCE_RISK proceeds. `(source, source_ref)` is unique (no duplicate approvals per debate or card); decisions are row-locked and idempotent; a late decision gets the timeout. An approved ADD_RISK order passes the mandate check only with the **command it is bound to** (`ai_approvals.command_id`), so an approval id cannot be replayed onto another command. The sweeper runs in the orchestrator, not in the (optional) notifier, so a REDUCE_RISK timeout proceeds even when Telegram is down.
7. **The Brain order card and the debate approval go through approvals.** The card approval stays server-side and idempotent (claim first, then an APPROVED `ai_approvals` row and one bound command, key `brain-card:<session>:<card>`); it resolves the mandate (the named one, else the single ACTIVE mandate allowing the instrument) and is refused without one. Approving a debate that already has an open approval decides that approval instead of queuing a second order.
8. **Notifier (`services/notifier`)**: Telegram Bot API over httpx with long polling (no webhook, no inbound port); only `TELEGRAM_ALLOWED_CHAT_IDS` are served, anything else is dropped and logged without a reply; button data carries an HMAC tag; veto and REDUCE_RISK approval are one tap; approving ADD_RISK asks for the operator's TOTP and deletes the code message. Decisions are HMAC-signed calls with a single-use nonce to `POST /api/v1/ai/notifier/approvals/{id}`; the API re-checks the chat allow-list, the TOTP (`NOTIFIER_OPERATOR_USERNAME`'s secret, replay-protected) and the approval state. Critical alerts go to Telegram **and** ntfy. `kill_switch.send_alert` queues on `notifier:alerts` (Slack only as a legacy fallback). The httpx URL logger is silenced so the bot token never reaches logs.
9. **Autonomy ladder** (`cryptonite_execution.autonomy`): a pure state machine. Promotion is one level at a time, only from a system proposal, only with operator TOTP and a gate that still passes at confirmation. Demotion is automatic (breach, drawdown ≥ ½ stop, hard stop, backstop). Leaving L3 withdraws the perps opt-in. The gate is measured from the DB since `level_since`: days, closed trades, max drawdown, `BREACH` events, daily Sortino vs BTC hold (the tracker stores the BTC price with each snapshot), veto rate at L2. Unmeasured numbers fail the gate.
10. **`DEBATE_EXECUTION_MODE` is deleted** (code, and the `system_settings` row in migration `026`). The debate worker routes verdicts by mandate level (`services/debate_worker/mandate_routing.py`): no mandate → operator; L1 → approval; L2 → veto window; L3 → queued; reductions immediate at L2/L3, a proceeding veto window at L1.

## Evidence

- Property tests (hypothesis, 2 000 + 400 examples): no accepted AI order escapes its mandate; the mandate check only adds rejections to the dispatcher and never edits the intent; the dispatcher's 25%/1% constants are unchanged.
- Replay test on a migrated DB with the real command poller: 50,000 → 52,000 (new HWM) → 46,500 (−5.4%: L3 → L2, once) → 30,000 (−21.6%: HALTED at L1, close queued) → the poller sells exactly the mandate's 0.1 BTC out of an account holding 0.6 → 60,000 does not un-halt and new risk is refused. Account backstop: kill switch latched in memory and DB, every mandate HALTED at L1, one close per AI position, no duplicate close or alert on the next pass.
- Approvals: ADD_RISK timeout → EXPIRED, no command; REDUCE_RISK timeout → EXPIRED_PROCEEDED with its CLOSE_POSITION; L2 veto window inside/outside active hours; racing approve/veto has one winner; a forged command reusing an approval id is rejected; a proceeded L2 window is rejected after a demotion to L1.
- Notifier against a mocked Bot API (httpx.MockTransport): foreign chats dropped with no call at all; forged button data refused; ADD_RISK asks for TOTP before any API call; signed request verified; token absent from logs; Critical alerts reach Telegram and ntfy. The real signed endpoint: bad signature / replayed nonce → 401, foreign chat → 403, ADD_RISK without or with a wrong TOTP → 401 (and the approval stays PENDING), valid TOTP → APPROVED.
- Every §4.5 transition has a unit test; a property test shows that no trigger other than a confirmed promotion ever raises the level.
- Test totals are in the PR and in HANDOFF (Phase 5).

## Deviations from the blueprint (and why)

| Blueprint | Implemented | Why |
|---|---|---|
| §4.4 "`GuardedOrderDispatcher` gains a mandate check that runs after the existing invariants" | The check runs in the orchestrator's AI order path *before* the dispatcher and only rejects | The dispatcher is synchronous and does no DB I/O by design; the mandate needs DB state. Effect is the same: additive, the dispatcher still runs in full |
| Five reject codes | Plus `MANDATE_REQUIRED`, `_NOT_FOUND`, `_POSITION_PCT_EXCEEDED`, `_INSTRUMENT_CONFLICT`, `_POSITION_NOT_OWNED`, `_APPROVAL_REQUIRED`, `_NO_REFERENCE_PRICE`, `_INSTANCE_UNAVAILABLE` | Each is a distinct way an AI order could otherwise escape its mandate |
| Hard stop "flattens with reduce-only orders" | `CLOSE_POSITION` capped at the mandate's quantity | Spot has no reduce-only in the dispatcher; `CLOSE_POSITION` is the existing risk-reducing path (the exit monitor uses it) and works under the kill-switch latch |
| One endpoint `POST /api/v1/ai/approvals/{id}` for button presses | Web: `/api/v1/ai/approvals/{id}/decision` (session + CSRF); Telegram: `/api/v1/ai/notifier/approvals/{id}` (HMAC + nonce) | Two different authentication models; the route-guard regression test lists the signed route explicitly |
| TOTP for risk-adding approvals | TOTP from Telegram (D8); the web decision relies on the operator session (password + TOTP at login) + CSRF | As D8 states it; the web session is already second-factor authenticated |
| §7.1 "gateway degraded (banner naming which roles fell back)" | The banner names: kill switch latched, exit monitor down, notifier down, LLM spend ≥ 70% | The gateway does not record per-role fallbacks yet; adding that means touching the gateway (out of scope) |
| §7.1 Mission Control "equity curve vs BTC" | Served by `GET /api/v1/ai/mandates/{id}` (`equity_curve` with the BTC price); the card shows budget and drawdown meters, not a chart | Scope; the data is there for a follow-up chart |
| L3 gate "calibration within ±10 pp" | Not measured until A7.2: the L3 gate fails closed | No outcome labels yet (Phase 7) |
| `.env.example` placeholders | No `.env.example` exists in the repo; the variables are documented in HANDOFF (Phase 5) | Task said "if it exists" |
| Mandate editor: "changes that add risk require TOTP" | Also any change of active hours counts as risk-adding | Conservative: a wider window lets L2 veto windows proceed |
| Debate worker writes approvals through `cryptonite_execution.approvals` | Its own small SQL module using the shared schemas policy; an integration test proves the rows are decided by the same code | The debate worker image carries only `cryptonite_agents` and `cryptonite_schemas` (no Nautilus) |

## Known gaps

- The notifier container uses `env_file: ../.env` like the other services, so it receives secrets it does not need (Gemini, Binance). A dedicated env file is the least-privilege follow-up.
- An approval card is not edited when it is decided elsewhere (web vs Telegram); the API refuses the second decision (409) and the bot says so.
- Perps under a mandate are enforced (L3, opt-in, ≤ 5×) but untested end to end with a live perp position; AI perps stay out of the program goal (O1).
- The live Telegram test with a BotFather token is an operator step (see HANDOFF).
